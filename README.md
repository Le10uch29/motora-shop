# Araz Motors — оптовый магазин автозапчастей

Закрытый интернет-магазин запчастей с админ-панелью. Покупателей заводит
администрация, сами покупатели регистрироваться не могут. Витрина и каталог
доступны только после входа.

Языки интерфейса: грузинский (по умолчанию), русский, азербайджанский.

## Стек

- **Next.js 16** (App Router, Server Actions) и **React 19**, TypeScript.
  В этой версии Next.js есть ломающие изменения. Перед правками сверяйтесь с
  документацией в `node_modules/next/dist/docs/` (см. `AGENTS.md`).
- **Supabase**: Postgres с Row Level Security, Auth (вход по телефону или
  email), Storage для фото.
- **Tailwind CSS 4**.
- `xlsx` (SheetJS) — чтение Excel при импорте; `sharp` — подготовка фото.

## Быстрый старт

```bash
npm install
cp .env.example .env.local        # заполните переменные, см. ниже
npm run dev                       # http://localhost:3000
```

Пакет `xlsx` ставится не из npm, а с `cdn.sheetjs.com` (так его распространяет
SheetJS), поэтому для `npm install` нужен доступ к этому адресу.

Первый запуск с пустой базой:

1. Примените `supabase/schema.sql` (см. «База данных»).
2. Создайте первого админа:
   `npm run create-admin -- admin@example.com пароль Имя Фамилия [телефон]`.
3. Войдите на `/ka/admin/login` и дальше заводите сотрудников и покупателей
   в самой панели.

## Переменные окружения

Из `.env.example`:

| Переменная | Зачем |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Адрес проекта Supabase. |
| `NEXT_PUBLIC_SUPABASE_KEY` | Публичный (anon/publishable) ключ. Виден в браузере, поэтому права доступа задаёт RLS в базе. |
| `SUPABASE_SECRET_KEY` | Секретный (service role) ключ. Работает в обход RLS, нужен только серверу и скриптам. **Никогда не отдавать в браузер.** |

Необязательная:

| Переменная | Зачем |
|---|---|
| `ALLOW_DATA_RESET` | `true` показывает на главной админки блок «Обнулить статистику»: поставить дату отсечки продаж или удалить тестовые заказы. Нужен на время тестов, **в production не задавайте** — тогда раздела нет совсем. |

## npm-скрипты

| Скрипт | Что делает |
|---|---|
| `npm run dev` / `build` / `start` | Разработка, сборка, запуск собранного. |
| `npm run lint` | ESLint. |
| `npm test` | Тесты (Vitest). |
| `npm run seed` | Разово переносит бренды и тексты страниц в базу. Товары не трогает. |
| `npm run seed:categories` | Заводит стартовый справочник категорий. Идемпотентный: создаёт только недостающее, ничего не перезаписывает. |
| `npm run create-admin -- email пароль Имя Фамилия [телефон]` | Создаёт первого админа (учётка в Auth и профиль в `staff`). |
| `npm run optimize-images` | Подгоняет уже загруженные фото товаров под рамки сайта (WebP 800×600, 800×800, 200×200). Повторный запуск безопасен. |

Скрипты `seed`, `seed:categories`, `create-admin` и `optimize-images` берут
переменные из `.env.local` и используют секретный ключ. Запускайте их только
локально.

## Роли

| Роль | Что может |
|---|---|
| **Админ** | Всё: сотрудники, покупатели, товары и импорт, склады, бренды, категории, акции, заказы, журнал. |
| **Старший продавец** | Всё, что продавец, плюс добавлять продавцов (в том числе назначать роль существующему пользователю), добавлять покупателей и менять им пароль. |
| **Продавец** | Добавлять и редактировать товары, двигать статус заказа (собирается, отправлен), менять количество и цену в оформленных заказах. |
| **Покупатель (клиент)** | Смотреть витрину, собирать корзину (она хранится на сервере и видна с любого устройства), оформлять заказ. |

Права проверяются на сервере (`src/lib/auth.ts`, `src/lib/roles.ts`) и в RLS
базы. Скрытые в интерфейсе кнопки — только удобство.

## База данных

Вся схема лежит в одном файле `supabase/schema.sql`. Он идемпотентный: таблицы
создаются через `if not exists`, политики пересоздаются через
`drop policy if exists`, поэтому его можно запускать повторно.

Порядок применения:

1. Supabase Dashboard → **SQL Editor** → New query.
2. Вставьте `supabase/schema.sql` целиком и выполните (**Run**).
3. После обновлений кода, которые меняют схему, снова выполните файл целиком
   или только новый блок в его конце. Отдельные миграции с датой в имени
   лежат в `supabase/migrations/`.

Если изменение схемы и код выкатываются вместе, сначала выкатите код, потом
выполните SQL. Конкретный порядок указан в комментарии к каждой миграции.

## Импорт товаров из Excel

Админка → Товары → «Импорт Excel». Колонки определяются по заголовкам, и
сопоставление можно поправить вручную.

| Поле | Узнаётся по заголовку |
|---|---|
| Код продукта (обязателен) | «код продукта», «артикул», «sku»… |
| OEM | «оригинал», «origin», «oem». Несколько кодов через `/`; первый считается главным и виден на карточке и в инвойсе. |
| Цена, количество | «цена», «кол-во», «остаток»… |
| Название ru / az / ka | «название», «adı», «დასახელება» |
| Описание | «описание» |
| Марка, модель | «марка», «модель» |
| Фото | ссылка на картинку или картинка, вставленная прямо в ячейку |
| Год / Год от / Год до | «год», «год от», «год до» |
| Склад | «склад», «магазин» |

Повторы одного кода в файле склеиваются. Если цены у повторов расходятся,
берётся большая, а расхождение попадает в «Конфликты импорта».

### Марка, модель, годы и двигатель

Совместимость детали с машинами записывается в трёх ячейках (разбор — в
`src/lib/fitments.ts`):

```
Марка:  TOYOTA/BMW
Модель: PRIUS V/PRIUS C//G30/X5 (3,0-4,4)
Год:    2000:2002
```

- `/` в **марке** разделяет марки.
- В **модели** `//` закрывает группу моделей одной марки, а `/` разделяет
  модели внутри группы. Пример выше даёт Toyota Prius V, Toyota Prius C,
  BMW G30 и BMW X5.
- `///` в модели заканчивает список машин. Всё, что после него, становится
  **описанием** товара: `ASTRA H///1,6` — это Astra H с описанием «1,6».
- **Двигатель** пишется в скобках. Скобки только у последней модели группы
  относятся ко всей группе: `F10/GT/E70 (4,4-4,8 N63)` даёт
  F10 4,4 / F10 4,8 / GT 4,4 / GT 4,8 / E70 4,4 / E70 4,8. Если скобки стоят
  у нескольких моделей (`F10 (4,4)/GT (3,0)`), у каждой свои. Берутся объёмы
  (`4,4`, `4,8`); если объёмов нет, берётся сам текст (`N63/N55`).
- Число марок и групп моделей может не совпадать. Лишние марки остаются без
  модели, а лишние группы достаются последней марке.

Годы:

| Запись | Значит |
|---|---|
| `2002-2015`, `2002:2015` | с 2002 по 2015 |
| `2012`, `2012+`, `2012-` или только «Год от» | с 2012 и дальше |
| `до 2015`, `-2015` | по 2015 включительно |
| `—`, `?` | год не указан явно |
| пусто | годы берутся у предыдущей машины; если их нет нигде — год не указан |

Можно одна колонка «Год» с диапазоном на каждую группу
(`2000:2002//2010:2015`) или две колонки «Год от» и «Год до». Год, который не
указан, нигде не показывается, и фильтр по годам такой товар находит при
любом годе.

## Деплой (Vercel)

1. Импортируйте репозиторий в Vercel (фреймворк Next.js определится сам).
2. В Settings → Environment Variables задайте `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_KEY` и `SUPABASE_SECRET_KEY`. `ALLOW_DATA_RESET` в
   production не задавайте.
3. Для `npm install` при сборке нужен доступ к `cdn.sheetjs.com` (пакет
   `xlsx`).
4. Ограничение хостинга: Vercel не принимает запрос больше 4,5 МБ, поэтому
   фото при импорте отправляются пачками до 3 МБ.

Изменения схемы базы Vercel не применяет: SQL из `supabase/schema.sql` или
`supabase/migrations/` выполняется вручную в SQL Editor, в порядке, указанном
в миграции.
